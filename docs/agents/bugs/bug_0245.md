## Symptoms

The parse panics with `internal error: entered unreachable code` at
`lightningcss-1.0.0-alpha.72/src/values/percentage.rs:30`. The fuzz target
aborted, because its panic hook runs before `guarded_parse` can catch the
unwind.

In an app with the default `panic = "unwind"`, `guarded_parse` turns the
panic into an error and the CSS is dropped. **An app built with
`panic = "abort"` aborts.**

## Minimal reproduction

```css
p { opacity: min(1, NaN) }
```

Also `max(1%, NaN)`, `clamp(1%, NaN, 3%)`, and computed NaN:
`min(1, sqrt(-1))`, `log(-1)`, `pow(-1, 0.5)`, `mod(1, 0)`, `rem(1, 0)`,
`calc(infinity - infinity)`, `1e39 - 1e39`, `calc(1e39 * 0)`.

## Root cause

lightningcss can't order a NaN against the other arguments, so it keeps the
math function unevaluated. `Percentage::parse` assumes a percentage `calc`
always computes to a value and calls `unreachable!()` on anything else.

## Fix

The three lightningcss parses of untrusted text already run under
`cascade::guarded_parse` (bug_0238), so with unwinding the sheet, attribute
or declaration is dropped like unparseable CSS. This change pins that with
tests, and the fuzz targets' panic hook excuses exactly this panic
(`fuzz::is_known_upstream_panic`, pinned to the lightningcss version, file
and message).

A load-time scan was not used: NaN is reachable through arithmetic, so
refusing every route means evaluating `calc()`. The fix belongs in
lightningcss (U49). The README documents the `panic = "abort"` exposure.
