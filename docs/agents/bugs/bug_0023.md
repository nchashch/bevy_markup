# bug_0023 — Wiring on `HtmlUiBuilt` stacked up once updates kept elements

| field | value |
|---|---|
| ID | bug_0023 |
| Status | **fixed** (`c8ab00f`) |
| Severity | high (quickstart: one click added 1, then 2, then 3 coins; demo: every language switch nested another copy of each content document) |
| Component | `examples/quickstart.rs`, `examples/demo/shell.rs`; the `HtmlUiBuilt` docs (`src/html.rs`, `src/lib.rs`) that taught the pattern |
| Introduced by | `cfdb4b3` (in-place updates) |
| Discovered by | user report (quickstart clicks), then a reproduction of the same pattern in the demo |
| Discovery agent | user; reproduced by omp session, Claude Opus 5.5 (Anthropic) |
| Date | 2026-10-05 |
| Regression coverage | none automated (examples have no runtime tests); reproduced and verified with an in-app driver: three clicks → `coins` 1, 2, 3; demo `HtmlUi` count 5 → 5 across a language switch, viewports still `overflow-y: Scroll` + `ScrollArea` |

## Minimal reproduction

```rust
fn wire(built: On<HtmlUiBuilt>, elements: HtmlElements, mut commands: Commands) {
    if let Some(button) = elements.by_id(built.entity, "add-coin") {
        commands.entity(button).observe(|_: On<Pointer<Click>>| { /* coins += 1 */ });
    }
}
```

Click three times: `coins` goes 1, 3, 6.

## Root cause

Until `cfdb4b3` every content update replaced every element, so wiring
attached on each `HtmlUiBuilt` landed on fresh entities, once each. Updates
now keep matching elements, and `HtmlUiBuilt` still fires after each one:
each click changed the context, the update kept the button, and the next
`HtmlUiBuilt` added another observer. The demo's `wire_shell_build` did the
same with content documents (spawned into kept slots again) and set
`Node.overflow` by hand, which every update overwrites (it re-inserts the
spec's `Node`).

The library's own documentation recommended the pattern ("attach behaviour
here").

## Fix

- quickstart: the button is `data-on-click="add-coin"`, read as
  `ElementSignal`s.
- demo: the viewports are `<div is="content-slot">` (a custom element
  definition adds `ScrollArea` and spawns the slot's document once per
  element); scrolling is CSS `overflow-y: scroll`, newly supported
  (`overflow`, `overflow-x`, `overflow-y`; `auto` scrolls).
- `HtmlUiBuilt`'s docs (and the crate guide, README, AGENTS.md) now say
  handlers must be idempotent and point to `data-on-*` and `is=` for
  behaviour; the doc example inserts a marker instead of observing.
