# bug_0016 — Rebuilding an `HtmlUi` whose subtree holds another rebuilding `HtmlUi` panics

**Status:** fixed (`9d21b17`, with the demo rewrite). **Severity:** high —
a plain app pattern (a nested `HtmlUi` inside another one, any change that
makes both rebuild in the same frame, e.g. an `ActiveLocale` swap) panics the
app.

**Component:** `src/build.rs` (`build_html_ui`).

## Symptoms

```
thread 'main' panicked at bevy_ecs-0.19.1/src/error/handler.rs:
Encountered an error in command `<Enable the debug feature to see the name>`:
Entity despawned: The entity with ID 449v0 is invalid; its index now has generation 1.
Encountered a panic when applying buffers for system `<...>`
```

The app dies on the frame where the updates are applied; nothing else is
corrupt (the frame simply never finishes).

## Discovery

- Reported by the user clicking a language button in the rewritten demo
  (commit `955e6ea` + uncommitted demo rewrite; the demo nests content
  `HtmlUi`s inside a full-screen shell `HtmlUi`'s slots).
- Agent: `zai/glm-5.3-flash:high`, 2026-10-05.
- Minimized to the headless vector
  `nested_ui_under_a_rebuilding_ancestor_is_skipped_not_panics`
  (`tests/html_ui.rs`), which panicked exactly like the demo before the fix.
  Earlier manual verification had clicked a *theme* button only — that path
  survived by iteration-order luck (theme clicks restyle the nested UIs
  instead of rebuilding them, and the restyle commands happened to queue
  before the shell's despawn), which is why it went unnoticed at first.

## Root cause

`build_html_ui` loops over every `HtmlUi`, decides, and *queues* commands.
With `ActiveLocale` swapped, every UI's `LocalizedText` changes, so both the
ancestor shell and the nested UI decide `Build` in the same run:

- the shell queues `despawn_related::<Children>()` + respawn — recursive, so
  it despawns the nested UI entity (a descendant through a slot element);
- the nested UI queues its own `despawn_related`/`apply_spec` commands for
  itself and its children.

Commands apply in queue order: once the shell's despawn ran, the nested UI's
queued commands target a despawned entity → panic. Whether it fires depends
on query iteration order (spawn order decides who queues first) and on
whether the nested UI rebuilds or merely restyles — an intermittent crash
that only needs a nested `HtmlUi` plus a coinciding update.

## Fix

`build_html_ui` now works in two passes: it gathers every entity's
`Decision` first, collects the entities deciding `Build`, and then — before
acting — skips any UI (build *or* restyle) that has one of those entities as
an ancestor. Such a UI is despawned by the ancestor's rebuild regardless of
what it decided, so acting on it is both moot and unsafe; `HtmlUiBuilt`
isn't triggered for it either. Apps that nest UIs re-nest them on
`HtmlUiBuilt` (as the demo's `wire_shell_build` does). Skips are logged at
`debug`.

## Regression test

`tests/html_ui.rs`
`nested_ui_under_a_rebuilding_ancestor_is_skipped_not_panics`: an `HtmlUi`
nested into an outer one's `#slot` element, then an `ActiveLocale` swap —
panicked before the fix; now the outer rebuild wins, the dump shows the
re-localized outer document, and the nested entity is asserted despawned.
