## Symptoms

Spawning an `HtmlUi` whose stylesheet asset **fails to load** (e.g. a CSS
syntax error) left the UI permanently blank: the `HtmlUi` root node existed,
no children were ever built, and no rebuild ever fired. The app logged
nothing; the panel just never appeared. A later hot-reload fix of the CSS
file *did* recover, but the initial failure was silent.

## Discovery

The `arbtest` harness (`tests/arbtest.rs`, 400 ms budget per property) feeds
lossily-decoded arbitrary bytes into each pipeline input and asserts the
pipeline settles and always leaves output. The `css` property failed within
its first search; arbtest printed the replay seed and the harness printed the
offending input.

- Reproducing seed: `0xfed8f5c900000020` (arbtest seed replay)
- Minimal offending input: CSS file containing `"\u{1a}\u{fffd}"`
  (control char + invalid-UTF-8 replacement), i.e. any CSS that fails
  lightningcss parsing.

## Root cause

`build_html_ui` gated the build on `Assets::<Stylesheet>::get(handle)`:

```rust
let css = match sheets.get(handle) {
    Some(css) => Some(css),
    None => continue, // "Still loading: its load event triggers the build."
};
```

`Assets::get` returns `None` both while the asset is **loading** and after it
has **failed**. A failed load emits no `AssetEvent`, so the `continue` path
was permanent: no event would ever mark the UI dirty again.

## Fix

Distinguish the two `None` cases with `AssetServer::load_state`:

- **Loading** → keep deferring (preserves the no-flash-of-unstyled-UI design;
  the load event rebuilds).
- **Failed** → treat the sheet as *absent* and build unstyled, browser-like.
  Because failures emit no asset event, the failure is latched in a
  `FailedSheets` resource so the unstyled rebuild happens exactly once; the
  latch clears on `LoadedWithDependencies`/`Modified` (hot reload).
  A failed per-entity `HtmlStylesheet` falls back to `DefaultStylesheet`.

(Follow-up hardening from bug_0004: the latch later became per-entity.)

## Regression coverage
