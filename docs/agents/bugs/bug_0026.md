# bug_0026 — Editing an included template never updates its users

| field | value |
|---|---|
| ID | bug_0026 |
| Status | **not a bug** — withdrawn 2026-10-06 after a file-watcher reproduction; see "Update: withdrawn" at the end |
| Severity | medium (breaks the hot-reload loop for template composition: editing a part, base or library include leaves every page stale until the page itself reloads) |
| Component | `src/template.rs` — `HtmlTemplateLoader` (`read_asset_bytes`) |
| Discovered by | writing the dependency vector (`template_dependencies_load_reload_and_fail`): the reload-the-dependency step never re-rendered |
| Discovery agent | omp session, zai/glm-5.3-flash:high |
| Date | 2026-10-06 |
| Regression coverage | `template_dependencies_load_reload_and_fail` (`tests/html_ui.rs`) pins the working half: reloading the *using* template re-reads the dependency and re-renders |

## Minimal reproduction

`pages/page.html`:

```
{% extends "base.html" %}
{% block body %}{% include "part.html" %}{% endblock %}
```

`pages/part.html`: `<p id="part">{{ n }}</p>`. Spawn the page, then edit
`pages/part.html` (with `file_watcher` enabled, or via
`AssetServer::reload("pages/part.html")`): `part.html` reloads (standalone,
once a handle exists), but the page keeps rendering the old part — no
`LoadedWithDependencies` for the page, no re-render. `reload` on the
*page's* path re-reads the part's fresh bytes and re-renders.

## Root cause

The loader reads included templates with
`LoadContext::read_asset_bytes`, which records them as **loader
dependencies** (`AssetInfo::loader_dependencies`, path + content hash). In
Bevy 0.19 those participate only in processed-mode re-processing and
handle-drop cleanup (`loader_dependents` is written in
`process_handle_drop_internal` and read nowhere else) — they are **not**
part of the reload-invalidation graph, and an unprocessed-mode file watcher
routes through `AssetServer::reload`, which acts only on *handles to that
path*. `part.html` never got a handle, so nothing reloads the pages that
include it. The module doc's "editing one reloads every template that uses
it" doesn't hold in unprocessed mode (and only by hash-detection in
processed mode).

## Fix

Non-trivial: the loader deliberately embeds every referenced template in
one `tera::Tera` instance (so `{% include %}` renders), which conflicts
with registering each dependency as its own tracked asset
(`load_context.load` would give real edges but separate `Tera`s). Options:

- watch the loader dependencies in bevy_markup (poll or a watcher handle)
  and re-load the root templates whose deps changed; or
- `LoadContext::load` the dependencies as labeled sub-assets of the root
  (`root.html#part`-style), keeping one Tera per root but with real edges;
- document the actual contract (reload the using template) and drop the
  overclaim.

## Workaround

`AssetServer::reload` the page's own path (or re-`load` its handle): the
loader re-runs and reads every dependency's current bytes.

## Update: withdrawn (2026-10-06, omp session, Claude Opus 5.5 (Anthropic))

The reported behaviour is real only for a **manual**
`AssetServer::reload("pages/part.html")`, which is what the reproduction
above (and `template_dependencies_load_reload_and_fail`) actually ran. With
a file watcher, editing an included or extended template **does** reload
every template using it, as `src/template.rs`'s module doc and ADR 0012 say.

**Source** (bevy_asset 0.19.1):

- `server/info.rs:503–531`: while `watching_for_changes`, a finished load
  records each loader dependency's reverse edge in
  `AssetInfos::loader_dependents` (so "written in
  `process_handle_drop_internal` and read nowhere else" above is wrong).
- `server/mod.rs:2116–2153` (`handle_internal_asset_events`): a source
  `ModifiedAsset(path)` / `AddedAsset(path)` event runs `reload_path`, whose
  `queue_ancestors` adds every (transitive) loader dependent to
  `paths_to_reload`, then `reload_internal`s each.
- `AssetServer::reload(path)` calls `reload_internal` for that path only. It
  never consults `loader_dependents`; that is Bevy's design, not a
  bevy_markup defect.

**Reproduction** (throwaway crate, deleted afterwards). Headless app with
`MinimalPlugins`, `AssetPlugin { watch_for_changes_override: Some(true),
meta_check: Never }`, `ImagePlugin` and `BevyMarkupPlugin`; bevy feature
`file_watcher`. The temp asset dir held the reproduction's `pages/page.html`,
`base.html` (`<div>{% block body %}{% endblock %}</div>`) and `part.html`
(`<p>v1</p>`). Only `page.html` was loaded; then each file was rewritten on
disk, and `page.html`'s `AssetEvent`s were printed with its output
(`render_source`):

```
LoadedWithDependencies at 0.0s → <div><p>v1</p></div>
edited part.html only
LoadedWithDependencies + Modified at 2.3s → <div><p>v2 edited</p></div>
edited base.html only
LoadedWithDependencies + Modified at 4.3s → <section><p>v2 edited</p></section>
```

No handle to `part.html` or `base.html` existed.

**What remains true** (documented, not a defect): code that reloads by hand
must reload the *using* template, because `AssetServer::reload` on a
dependency only reloads the dependency. Hot reload also requires Bevy's
`file_watcher` feature, which bevy_markup's own dev builds don't enable.

No permanent test was added. It would need `file_watcher` in the
dev-dependencies and would wait on real filesystem events, so it would be
slow and timing-dependent.
