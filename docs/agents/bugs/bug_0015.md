| field | value |
|---|---|

| Severity | medium (process abort from a translation file; needs a pathological input of a few KB) |
| Component | upstream `fluent-syntax` 0.11.1 parser (`vendor/fluent-syntax/src/parser/`), reached from any FTL bundle asset |
| Discovered by | the fuzz-corpus coverage replay (`tests/fuzz_corpus.rs`), first run |

## Symptoms

Parsing FTL with deeply nested placeables (`x = {{{…"a"…}}}`) aborts the
process with `thread '…' has overflowed its stack`. In a p23 app the parser
runs inside bevy_fluent's bundle loader on a task-pool thread, so a crafted
or corrupted translation file of a few KB crashes the app.

## Discovery

Replaying the cargo-fuzz `ftl` corpus through `p23::fuzz::translate` in a
debug test aborted on stack overflow. The corpus held inputs nesting
placeables up to 1053 levels deep (in ~1.1 KB). libFuzzer never flagged
them: it runs an optimized build on the 8 MB main thread, where that depth
fits.

## Minimal reproduction

```rust
let ftl = format!("x = {}\"a\"{}\n", "{".repeat(depth), "}".repeat(depth));
fluent::FluentResource::try_new(ftl); // stack overflow for large `depth`
```

Overflow depth (parse alone; formatting adds nothing on top), measured:

| build | 2 MB stack (spawned thread) | 8 MB stack (main thread) |
|---|---|---|
| debug | 200–400 | 800–1600 |
| release | 1600–3200 | 6400–12800 |

## Root cause

fluent-syntax parses placeables and inline expressions recursively, with no
nesting limit.

## Fix (proposed)

Add a nesting-depth limit to the vendored parser (e.g. a counter through the
placeable/inline-expression recursion that returns a parse error past a fixed
depth such as 100), next to the existing `[patch.crates-io]` patch for
bug_0005. Then a regression test parsing a depth far beyond the limit on a
2 MB thread, and drop the large stack from `tests/fuzz_corpus.rs`. Report
upstream.
