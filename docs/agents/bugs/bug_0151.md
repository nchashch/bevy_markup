## Symptoms

Reproducible by the project owner: `testbench --scenario big-document
--size 10000 --no-churn --windowed`, scrolling down with the mouse
wheel. Two observed behaviors:

1. **The visible list thins as the user scrolls down** — fewer and
   fewer rows render in the panel, down to none — and reappears around
   the ~1000th row. ("The items start disappearing — the visible
   viewport list gets shorter and shorter until there are no items —
   before scrolling down to 1000 items.")
2. **Hovering the not-culled items changes the visible count** — more
   items appear while in the "scrolled down" state.

The user's phrasing of the state: "materialized view != visible
content"; the rows "disappear above the upper fold of the panel".

A mid-sweep screenshot (the MCP harness, `mcp_harness/screenshots/`)
showed: the shell fully rendered, the stage panel **empty**, while
`game/ui` reported 65 materialized rows at on-screen rects and the live
counts read "elements 279" — the ECS right, the screen wrong.

## Investigation so far (all verified, none sufficient)

- **The model is exact at probe time**: 10000 entries, total 200000 px
  (headless, scale 1), matching the layout's content size (200132).
  The user's display's scale factor is 1 (probed live), so the
  physical/logical conversion (fixed in `77086c8`) is a no-op for
  them — that fix was correct math but not the user's bug.
- **The probe at each scroll depth** showed a constant materialized
  count (65 rows, 2 spacers) with the component scroll, the layout's
  applied scroll and the model's total all consistent — but a later
  `game/ui` dump caught the band's rows laid out at **negative y**
  (~11000 px above the viewport) while the scroll position said they
  belonged on screen: the band was built for a scroll offset ~75
  frames stale.
- **Fix attempts committed**:
  - `77086c8` — the heights in logical pixels (`inverse_scale_factor`).
  - `5f8e673` — (a) re-measure on `Changed<ComputedNode>` (the model
    self-corrects after fonts load; hover's re-cascades no longer
    shuffle which heights are current); (b) a matched element whose
    laid-out children no longer count-match the spec's is replaced,
    gated on windowing (the old count-mismatch guard skipped the whole
    update forever — a nested-UI race fix that the moving band tripped
    on every scroll frame).
  - The `--scroll` sweep fixed to drive the scroll position in logical
    units over the full content range.
- The headless vector (`windowed_build_materializes_the_band_and_spacers_the_rest`)
  and the scripted sweep both behave correctly at every depth; the
  interactive wheel-driven path is where the symptoms persist. The
  wheel mock in `game/mouse` cannot drive this (it feeds input
  resources, not the `MouseWheel` messages the picking backend reads),
  so the scripted sweep is the only automated stand-in — and it does
  not reproduce.

## Open hypotheses

1. **The stale-band frame path is still reachable interactively**: the
   dump caught the band ~75 builds stale; the replace-on-mismatch and
   the re-measure should both have corrected it, but the wheel path
   (picking `PointerScroll` → the widget's `ScrollPosition` write →
   the rebuild) interleaves with hover-flip restyles in a way the
   scripted sweep (one big jump per frame, no pointer) never
   exercises. The restyle path's band handling (a `Decision::Restyle`
   frame with a moved scroll) is the least-inspected corner.
2. **The interaction between the `ScrollArea` widget's clamping and the
   band**: bevy's widget clamps `ScrollPosition` against
   `content_size − visible_size`, both derived from the *current*
   (partially-spacered) content; a drift between the model's total and
   the laid-out content changes what the user can scroll to.
3. **A second units/conversion error in the real-window path** that
   the headless probe cannot see (its scale factor is 1 and its root
   was 0×0 until the `--scroll` runs).

## Reproduction pointers

- `testbench --scenario big-document --size 10000 --no-churn
  --windowed`, scroll down with the wheel (a focused window).
- The `CULLPROBE` diagnostic logs the scroll, the layout's applied
  scroll, the content extent, the materialized/spacer counts and the
  model health every 60 frames (`scroll_workloads` in
  `examples/testbench/main.rs`).
- `game/ui` over the MCP harness (port 15702, the `dev-tools` feature)
  dumps the laid-out nodes with rects; `game/screenshot` captures the
  real frame.

## Root cause (review_0006 J01)

**Coalesced spacers dropped the row gaps.** `coalesce_spacers` merged a
run of k culled siblings into one spacer whose height was the sum of the
members' heights. In a column with a row gap, k nodes are spaced by k − 1
gaps, but one node gets none inside it, so the merged spacer was
(k − 1) × gap too short. The cursor that decides the band (`collect_items`'
root loop, `collect_node`'s `ys`) adds `outer + gap` per row. The band was
computed for the true positions, but the materialized rows landed
(culled above − 1) × gap higher. The testbench's root gap is 2 px, so
past ~600 culled rows the error exceeded the band's one-viewport margin
and the panel emptied. 5 500 culled rows put the band ~11 000 px above
the viewport, the figure the `game/ui` dump caught.

A second error in the same cursor: the root loop advanced by
`win.frames.borrow().last()`'s gap. That is the root frame's until the
first materialized container pushes its own; then it was a row's
`gap: 8px`. The band's lower edge fell short of the viewport's (hidden by
the margin).

### Why the investigation missed it

- The probes compared the model's total (200 000, heights only) with the
  laid-out content (200 132 = the heights + the 66 gaps of the
  *spacered* layout). Both lacked the same gaps, so they agreed. The
  real document is 219 998 px.
- The scripted `--scroll` sweep does reproduce it. Run offscreen at
  `bd99546` it shows an empty stage mid-sweep, but it was judged by the
  materialized count (constant 65), which was right.
- The headless vector's root has no gap, and it checks which rows exist,
  never where they are laid out.
- The physical/logical conversion (`77086c8`) and the re-measurement
  (`5f8e673`) were real but unrelated (the owner's scale factor is 1),
  and the units fix is incomplete (review_0006 J03).

## Fix

`Item::Spacer { height, gap }` carries the gap of the column it was culled
from (`WindowCtx::culled`); `coalesce_spacers` adds one gap per merge; the
root loop reads the root frame's gap. Verified with an unwindowed build as
the oracle (every materialized row within 1 px, every viewport row
materialized) at several depths, in the testbench's row shape and after a
hover restyle, and in the testbench itself offscreen: rows render
throughout the sweep, the content extent reads 219 998 px.

The second symptom (hovering changes the visible count) was not
reproduced separately; the hover regression test passes with the fix.
