## Symptoms

Parsing certain FTL sources aborted the process (Rust panic → SIGABRT under
the fuzzing runtime):

```
thread '…' panicked at fluent-syntax-0.11.1/src/parser/slice.rs:24:
end byte index 100 is not a char boundary; it is inside '�' (bytes 99..102 of string)
```

libFuzzer reproduction confirmed the same panic outside honggfuzz. In a p23
app, any FTL bundle asset with such content crashes the app at load — the
parser runs inside bevy_fluent's bundle loader.

## Discovery

The honggfuzz `ftl` target (arbitrary bytes split on `\n---\n` into FTL body,
message id, args JSON) reported `crashes_count: 2386` in a 120 s, 4-thread
run; honggfuzz saved one representative crash file plus
`HONGGFUZZ.REPORT.TXT` (SIGABRT). The input was minimized with
`cargo fuzz tmin` to a 17-byte case.

## Minimal reproduction

FTL source (bytes): `u={"\\U` followed by an invalid-UTF-8 byte
(`0xb1`, decoded to U+FFFD by the harness's lossy conversion) — i.e. a
broken `\U` unicode escape immediately after a multi-byte character. The
parser's error/escape handling computes a byte range (`ptr - 1` style
arithmetic) that lands inside the replacement character and `Slice::slice`
(`&self[range]`) panics. A second variant (from the same campaign family)
slices at fixed offset 100 across a multi-byte char in long error context.

## Root cause (upstream)

`fluent-syntax`'s `Slice::slice` for `String`/`&str` applies the parser's
byte ranges directly. Several ranges are computed with byte guesses
(`self.ptr - 1`, fixed windows like `[..100]`), which are not guaranteed to
be char boundaries. Checked upstream: **still broken in fluent-syntax
0.12.0**; and 0.11.1 is pinned by `fluent-bundle`/`fluent` 0.15/0.16, which
is required by bevy_fluent 0.15 — so the version cannot simply be bumped.

## Fix (local vendored patch)

`vendor/fluent-syntax` — a copy of the 0.11.1 crate wired via
`[patch.crates-io]` in the root, `fuzz/` and `honggfuzz/` manifests (the
patch must be declared per workspace). The patch clamps ranges to char
boundaries in both `Slice::slice` impls:

```rust
fn clamp_boundary(source: &str, index: usize) -> usize {
    let index = index.min(source.len());
    if source.is_char_boundary(index) { index }
    else { (index..).find(|&i| source.is_char_boundary(i)).unwrap_or(source.len()) }
}
```

(The clamp rounds *up*, matching the parser's intent of capturing the
surrounding error context.)

Crate lints are silenced at the top of the vendored `lib.rs`; the crate docs
in AGENTS.md note to re-check the patch when bevy_fluent is upgraded.

## Regression coverage

`src/fuzz.rs::tests` (feature `fuzzing`): the minimized 17-byte case and the
long-multibyte-error-context case, both asserted not to panic.

## Post-fix verification

honggfuzz campaign across all three targets after the patch:
29.6M / 44.7M / 79.7M iterations, zero crashes (ftl previously crashed
2386 times per 120 s).

## Notes

- Worth reporting upstream to the Fluent Rust project (rust-fluent/
  fluent-syntax); the fix is small and this input is a ready-made test case.
  If a future fluent-syntax release includes a boundary-safe `Slice`, drop
  the vendored patch and the `[patch.crates-io]` sections.

## Update (2026-10-05): one cause, fixed at the source

Writing the upstream fix showed the analysis above was partly wrong:

- **Single cause.** `skip_unicode_escape_sequence` quotes the invalid
  escape plus the character that ended it, sliced one *byte* past the
  escape (`ptr + 1`). That byte range ends inside a multi-byte character.
  The parser's other `ptr - 1` slices always follow an ASCII byte; with the
  vendored clamp removed, the escape test panicked, while ~4,900 ftl fuzz
  inputs (seeds plus a local corpus) replayed without a single panic.
- **No "second variant".** The long multi-byte error context input parses
  to an ordinary `ExpectedInlineExpression` error in fluent-syntax 0.11.1
  and 0.12.0, with or without the clamp. Its test,
  `long_multibyte_error_context_does_not_panic`, never exercised the bug
  and was removed.
- **Fix.** The fork takes the whole offending character
  (`chars().next().map(char::len_utf8)`), keeping the error message intact,
  instead of clamping every slice. `vendor/fluent-syntax` is gone; all five
  manifests patch fluent-syntax from the fork's git branch.
