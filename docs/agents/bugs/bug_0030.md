## Symptoms

In the `links` example, arrows / D-pad / left stick do nothing (the
example only bound ← → and LB/RB — that part was an example gap), and a
one-frame highlight never stuck. A throwaway driver pressing ← showed
`InputFocus` set by `cycle_links` and **`None` again by the end of the
frame**; the `PseudoState` read `focused: true` for one frame (the state
system ran before the repair that wiped it), then false.

## Root cause

`repair_focus` keeps the app's focus only when the focused entity is

- navigable (`Focusable` + `AutoDirectionalNavigation`), or
- a UI `Node` that is not a markup `Focusable` (an app widget).

A link span is neither: it has bindings (`ElementSignals`, so
`HtmlFocus::activate` can emit them) but no `Focusable` (no box to
navigate by) and no `Node`. Repair fell through to "stale" and cleared
the focus every frame.

## Fix

`repair_focus` also keeps the focus when the focused entity carries
`ElementSignals` — the exact set `activate_element` acts on, i.e. an
activation target the app focused deliberately.

## Example gap (same report)

The `links` example bound only ← → and LB/RB; D-pad and the left stick
did nothing by construction, and the repo convention is that arrows /
D-pad / stick move focus in every example. `cycle_links` now cycles on
all four directions via the shared `Arrows` axes with hold-to-repeat
(`Repeat`, now `pub` in `examples/shared/input.rs`), plus Q / E and
LB / RB one steps; the hint texts and README updated.
