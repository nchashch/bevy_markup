# bug_0021 — Despawning a UI in the same frame panicked `update_pseudo_states`

| field | value |
|---|---|
| ID | bug_0021 |
| Status | **fixed** (uncommitted at filing) |
| Severity | high (app crash: Bevy's default command error handler panics) |
| Component | `src/signals.rs` — `update_pseudo_states`; same pattern in `src/focus.rs` — `sync_navigation` |
| Discovered by | prototype_19 integration (headless smoke run: hover Connect for its tooltip, click it, client panicked on the state change) |
| Discovery agent | omp session, Claude Opus 5.5 (Anthropic) |
| Date | 2026-10-05 |
| Regression coverage | `signals::tests::pseudo_states_tolerate_a_same_frame_despawn` |

## Minimal reproduction

An element bevy_markup hasn't given a `PseudoState` yet (every element, the
first frame it's seen), and an app system in the same schedule that despawns
it with its command buffer applied before bevy_markup's:

```rust
app.add_systems(
    Update,
    (
        move |mut commands: Commands| commands.entity(element).despawn(),
        update_pseudo_states,
    )
        .chain_ignore_deferred(),
);
app.update(); // panicked: "Entity despawned: The entity with ID 8v0 is invalid"
```

In prototype_19: hovering a main-menu button spawns a tooltip `HtmlUi`;
clicking it (connect) tore down the menu and the tooltip in `Update` while
`update_pseudo_states` had queued `insert(PseudoState)` on the tooltip's new
element. The insert hit the despawned entity and the client exited with
code 101.

## Root cause

`update_pseudo_states` (and `focus::sync_navigation`, which inserts/removes
`AutoDirectionalNavigation` on every element each frame) queued plain
`insert`/`remove` commands on elements it saw in its query. The UI belongs
to the app, which may despawn it in any system of the same schedule; if that
despawn is applied first, a plain insert is an error, and Bevy's default
error handler panics.

## Fix

`try_insert` / `try_remove` in both systems: state bookkeeping on an element
that's gone is meaningless, so the command is skipped.
