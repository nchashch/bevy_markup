## Symptoms

p23 documents translations as "fluent-dom style DOM overlays", but ignored
`data-l10n-name`. With

```html
<p data-l10n-id="named">Visit <span data-l10n-name="place" class="hot"></span>.</p>
```

```ftl
named = Go to <span data-l10n-name="place">the tower</span> now.
```

fluent-dom renders "the tower" as the source `<span class="hot">` (red);
p23 used the translation's bare `<span>`, so the class (and any id) from the
source was lost and the text stayed unstyled.

## Discovery

The first run of the Fluent oracle (see bug_0006):

```
    p
+     "Go to the tower now." serif 20px #ffffff
-     "Go to " serif 20px #ffffff
-     "the tower" serif 20px #ff0000
-     " now." serif 20px #ffffff
```

## Root cause

Not implemented: translation markup was styled from its own elements only;
nothing linked a translated element to the source element of the same name.

## Fix

`walk_translation` collects the source element's `data-l10n-name`
descendants (document order) into the fragment context; `Ctx::element`
styles a named translation element as the source element (tag, id,
classes). As in fluent-dom's `getNodeForNamedElement`: a name with no source
element, or one of a different tag, renders as plain text; each source
element can be used once (a second reference is plain text). Unlike
fluent-dom, the named element's nested markup is kept (p23 doesn't sanitize
translations; a deliberate, documented difference).

## Notes

- fluent-dom's sanitizer (no nesting, no `class` from translations, only
  text-level elements) is *not* adopted; with it, named elements are
  fluent-dom's only way to style parts of a translation. p23 offers both.
