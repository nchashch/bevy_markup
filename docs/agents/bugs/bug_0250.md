## Symptoms

bug_0249 capped the computed font size at 8192 px against rasterizer
overflow, but memory stayed unbounded. Bevy keeps font atlases per exact
size, never frees them, and gives a large glyph an atlas of its own
(UPSTREAM U55). Measured in release (main-world bytes; the GPU holds as
much again):

- one glyph at 8192 px: 256 MiB; 16 letters at 8192 px: 2.3 GiB;
- 2,000 elements with sizes 10, 10.001, 10.002, … px: 2 GiB;
- 4,000 elements between 16 and 1016 px: 10.6 GiB in 11.5 s.

A tall glyph (`j`, `$`) at 8192 px also needs a 16384² atlas, past the
8192 px texture limit of WebGPU and many GPUs.

## Fix

`HtmlFontLimits` (a resource the app may set):

- `max_font_size`, default 2048 px (never above 8192): tall glyphs' atlases
  stay within 8192 px up to a scale factor of 2.
- `max_font_sizes`, default 128 distinct sizes across the app: past it a new
  size reuses the nearest size in use (by ratio), whose atlases Bevy keeps
  anyway. Counted sizes stay counted, as Bevy's atlases stay allocated.

The budget is applied where the computed style is made, so text, `em`
lengths and letter spacing all use the same size. Each size costs at least
1 MiB, so with the defaults distinct sizes cost about 128 MiB plus their
glyphs; how many glyphs a page draws (one atlas per large glyph) is still
unbounded, which only an atlas budget in Bevy could fix.
