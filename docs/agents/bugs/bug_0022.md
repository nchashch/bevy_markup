# bug_0022 — In a windowed app, `autofocus` never took focus

| field | value |
|---|---|
| ID | bug_0022 |
| Status | **fixed** (uncommitted at filing) |
| Severity | high (keyboard/gamepad navigation dead in every windowed app until the first click) |
| Component | `src/focus.rs` — `repair_focus` |
| Discovered by | smoke run of the new `menu` example (in-app driver: arrows/Enter did nothing, `InputFocus` never on an element) |
| Discovery agent | omp session, Claude Opus 5.5 (Anthropic) |
| Date | 2026-10-05 |
| Regression coverage | `focus_on_the_window_yields_to_autofocus` (`tests/html_ui.rs`) |

## Minimal reproduction

Any app with `DefaultPlugins` (a primary window) and an `HtmlUi` with an
`autofocus` element:

```html
<div id="a" data-on-click="a"><p>A</p></div>
<div id="b" autofocus data-on-click="b"><p>B</p></div>
```

`InputFocus` stays on the window entity; `HtmlFocus::navigate` and
`activate` do nothing; no `:focus-visible` ring. A mouse press focuses a
button and everything works from then on. Headless runs (tests, prototype_19's
`--mcp` client) have no window and never showed it.

## Root cause

`bevy_input_focus`'s `InputDispatchPlugin` runs `set_initial_focus` in
`PostStartup`: with nothing focused, it focuses the primary window.
`repair_focus` deliberately leaves focus on non-markup entities alone (so an
app's own UI can hold focus) and counted the window as such an entity.

## Fix

Only a UI node (an entity with `Node`) that isn't markup keeps focus; focus on
anything else — the window — counts as nothing focused and is repaired to
the remembered, `autofocus` or first element. With nothing focusable in
scope it's cleared, and Bevy's dispatch falls back to the primary window as
before.
