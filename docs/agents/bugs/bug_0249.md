## Symptoms

Parsing refused non-finite numbers, but finite values near `f32::MAX`
overflowed later, inside Bevy:

| Declaration on an element holding text | Debug build | Release build |
|---|---|---|
| `width: calc(3e38px + 1em + 3e38px)` (also `margin`, `flex-basis`) | parley panic | parley panic |
| `top: calc((3e38px + 1em + 3e38px) + (-3e38px + 1em - 3e38px))` (NaN) | bevy_ui panic | bevy_ui panic |
| `width: 3e38em`, `width: 3e38vw`, `padding: 3e38px`, `border-width: 3e38px`, `width` + `margin-left` near `f32::MAX` | parley panic | parley panic |
| `height` or `max-width` resolving to NaN | no crash; the node is rewritten every frame (NaN ≠ NaN), dirtying layout | same |
| `font-size: 2e5px` and larger | zeno panic (`u32` overflow) | hangs (> 2 min at 100% CPU, 1.4–2.4 GB) |
| `font-size: 50000px` | — | 3.5 s and 6.9 GB for one glyph |

Widths and margins up to `1e9px` and font sizes up to `1e6px` laid out
fine in the tests: the crashes need an overflow to infinity (or NaN) in
layout's sums and products, or a glyph past zeno's `u32` bitmap size. All
of it predates ADR 0048: lightningcss passed the same values through.

## Root cause

- A mixed-unit `calc()` is kept as an expression and added up per frame by
  `CalcExpr::resolve`, which didn't check the result.
- Bevy multiplies `em`/`vw` and adds widths, margins, paddings and borders,
  so two values near `f32::MAX` make infinity.
- Relative font sizes multiply down the tree, and nothing bounded the
  computed size.

## Fix

- `css::value::MAX_CSS_MAGNITUDE` (10⁸): every parsed length, percentage
  and number (and every `calc()` term) is clamped to it, as browsers clamp
  huge lengths. No sum or product the layout forms can overflow then.
- `CalcExpr::resolve` skips a non-finite result and clamps the rest.
- `FontSizeSpec::resolve` clamps the computed size to
  `cascade::MAX_FONT_SIZE` (8192 px), below the glyph sizes that crash or
  hang. What a glyph of up to 8192 px costs in memory is still open.
