# bug_0256 — `tojson` with a huge indent allocated gigabytes

| field | value |
|---|---|
| ID | bug_0256 |
| Status | **fixed** in bevy_markup's `tojson` wrapper (the commit after `3b4253d`); MiniJinja itself unfixed (UPSTREAM U64) |
| Severity | high (DoS: a 93-byte template allocates GBs and stalls its render) |
| Component | `src/template.rs` (`checked_tojson`, `fits_printed`); minijinja 3.1.0 (`json::JsonWriter`) |
| Discovered by | cargo-fuzz `html`, Nightly run 45997844575 (2026-11-27): one timeout |
| Discovery agent | Claude Code session, `claude-opus-5-5` |
| Commit at discovery | `3b4253d` |
| Date | 2026-11-28 |
| Regression coverage | `template::tests::tojson_indents_count_toward_the_printed_size` |

## Symptoms

The input took over 10 s under ASan and peaked at 2.6 GB, inside
MiniJinja's `JsonWriter::write_indent`, called from `tojson`.

## Minimal reproduction

```
{{ [1] | tojson(5E13) }}
```

## Root cause

MiniJinja's `tojson` accepts any `usize` as its indent (`5E13` converts)
and writes `indent × depth` spaces before every item into a `String`;
the result is charged to fuel, if at all, only after it is built
(UPSTREAM U64). bevy_markup's wrapper bounded the number of items a
printed value holds (bug_0253), not the bytes each item's indentation
adds.

## Fix

`checked_tojson` reads the indent as MiniJinja does (`true` = 2, `false`
or none = 0, else a `usize`, positional or `indent=`), and
`fits_printed` charges each item `3 + 2 × indent × depth` bytes (its own
line and at most its container's closing line) against
`MAX_RENDERED_BYTES` before MiniJinja writes anything. Ordinary indents
are unaffected; `{} | tojson(5E13)` still prints `{}`. The fuzz input now
finishes in 1 ms. Without the indent counted, the test's
`([1] * 3000000) | tojson(4)` builds 21 MB before the output limit
refuses it.
